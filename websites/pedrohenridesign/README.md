# Pedro Henri Design Website

Portfolio of Pedro Henri Design (`https://pedrohenridesign.com.br`). Astro SSR on
Cloudflare Workers, with its content managed in
[EmDash](https://github.com/emdash-cms/emdash): the admin lives at
`/_emdash/admin` on the site itself.

## Stack

- Astro SSR on Cloudflare Workers + Assets
- EmDash CMS: isolated Cloudflare D1 and R2 with native Access authentication
  for PR previews; Turso (libSQL), S3-compatible media and default passkeys
  for standard staging/production builds. Local development uses SQLite and
  `.data/uploads`. All deployed flavors use the `SESSION` KV binding
- Tailwind CSS v4 via `@tailwindcss/vite`
- `@vandal-websites/sun-ui` for the layout, image and icon primitives
- Images go through the shared image service (`apps/images`) at request time;
  there is no `ipx` and no image transform in the Worker

## Content model

Everything below is edited in the admin; the site code only renders it.

- **Categories** (`categories`, served at `/categorias/{slug}`): name,
  description, share image, home page position, button text and the "process"
  steps (icon, title, description). `showcase` is the position on the home
  page; `0` keeps a category off it. Each category lists its posts, newest
  first (the **Posts** field is the other end of the post's Category link).
- **Posts** (`posts`, served at `/posts/{slug}`): title, description, cover,
  share image, a Category and **Content**, an ordered list of blocks:
  - **Text**: rich text in a centered column, with an optional hex background,
    light/dark text and rounded corners.
  - **Image**: one full-width image, optional background and rounded corners.
    Round the first and last image of a group so the group reads as one card.
  - **Text and image**: a text column next to an image (image left or right).
  - **Colored cards**: a row of cards, each with its own background and text
    color.
- **Drafts**: the old site's `private: true` content (an "Arquivo" category and
  a lorem ipsum post) was never served, so it is seeded as drafts.

Kept in code on purpose: the home page copy and hero, the header navigation,
the footer call to action, and the WhatsApp number.

## Local development

```sh
env -u CI moon run pedrohenridesign:seed   # once, and again after resetting .data/
env -u CI moon run pedrohenridesign:dev
```

Stop the site's running dev server before seeding, then restart with the dev
command above. The shared seed task first snapshots existing byline IDs to
`.data/seed-byline-locale.pending.json`, runs the CLI, and repairs only newly
created, conflict-free seed bylines from `en` to the seed's default locale.
Pre-existing rows are never relabelled. A failed run retains its snapshot for
retry; malformed or seed-mismatched snapshots fail closed. No snapshot means no
repair. Pedro's current seed contains no bylines and needs no snapshot.

`astro dev` runs on Node with SQLite at `.data/emdash.db` and uploads in
`.data/uploads` (both gitignored). No credentials are needed. `seed` (shared
by every EmDash site, `.moon/tasks/emdash.yml`) applies `seed/seed.json` to
the local database, downloading each image into `.data/uploads`, then
`scripts/seed-extensions.ts` writes what the `emdash seed` CLI ignores: the
`seo` panel of the home entry and the **Settings > SEO > Default Social Image**
(a `$media` value). Open `http://localhost:4321/_emdash/admin` and run the
setup wizard, or `GET /_emdash/api/setup/dev-bypass?redirect=/_emdash/admin`
to sign in as a dev admin (development only). Workflow and format details:
[`docs/guides/emdash-local-development.md`](../../docs/guides/emdash-local-development.md).

Reset the local database and uploads:

```sh
(cd websites/pedrohenridesign && bunx astro dev stop && rm -rf .data)
```

`emdash-env.d.ts` is generated by EmDash from the database schema on every dev
server start and is tracked; commit it with any schema change.

## The seed

`seed/seed.json` is the schema (collections, fields, block types, relation)
plus the site's content. It is read at build time, applied to an empty
database on the first request (schema), and never automatically reapplied to
an existing database. Images are `$media` references with absolute URLs to
the original production bucket; local and preview seeding downloads them into
isolated media storage, so the repository holds no images or database.

For staging/production, complete the wizard with content OFF, then run `bun scripts/deploy.ts seed-content pedrohenridesign --stage <stage>` with that stage's secrets to reuse canonical media keys and apply the settings, SEO and byline extensions; see the [first-time setup guide](../../docs/guides/provision-new-site-and-rotate-secrets.md#first-time-cms-content-on-staging-and-production).

Seeds cannot set publish dates, so each entry is published when the seed is
applied and the lists sort newest first by that time. Posts are therefore listed
oldest first in the seed; keep that order when editing it.

Changing `seed/seed.json` does not touch an existing database. Make model
and content changes in the admin; to inspect what the admin changed against the
committed baseline, export the local database itself to a temporary file (do
not seed a scratch database first, which would export the seed, not your edits,
and do not overwrite `seed/seed.json` automatically):

```sh
cd websites/pedrohenridesign
bunx emdash export-seed --database ./.data/emdash.db --with-content=all \
  --media-base-url=<S3_PUBLIC_URL> > /tmp/exported.json
```

The installed EmDash export does not include extension-managed per-entry SEO
panels or byline custom fields and their values. Preserve those instead of
treating the export as a complete backup. Portable site settings, including
`seo.defaultOgImage`, are exported; inspect their media references too.

`export-seed` rewrites top-level image fields as `$media` URLs on the local
site (`<base>/_emdash/api/media/file/<key>`) and leaves images inside blocks
and Portable Text as stored local values (id and storage key), neither of
which resolves on another site. Rewrite both to the real
`<S3_PUBLIC_URL>/<path>` URLs before
committing, then check it with `bunx emdash seed seed/seed.json --validate`.

## Images

CMS images render with `SunPicture` from the media value's stored dimensions:
the source is the bucket public URL (or the site's
`/_emdash/api/media/file/<key>` route) and the image service transforms it at
request time through `IMAGES_BASE_URL` (the Worker variable `getSecret` reads).
Assets referenced from code (hero, footer and header images) use
`src/utils/images.ts`, which builds their public URL from the request-time
`S3_ENDPOINT` and `S3_BUCKET` values instead of a hard-coded bucket hostname.
Pictures use blur-up placeholders only with the image service configured.

Local development leaves `IMAGES_BASE_URL` empty (`.env`, seeded from
`.env.example` with `cp .env.example .env`): pages serve the originals, the
seeded media from `.data/uploads` and the code assets from the bucket. The
image service is not used locally; it cannot fetch the dev server's own
`localhost` media. PR Previews do the same on purpose
(deploy gives them an empty `IMAGES_BASE_URL`): the external image
service cannot authenticate to the Access-protected origin (tracked in #196), so
they serve originals directly, with no `/_image` or transformed `srcset`.
Staging and production use the image service.

Code-owned branding assets still read the staging bucket in development and
PR previews. Set `S3_ENDPOINT` and `S3_BUCKET` from Infisical's staging values
in the local `.env` and this Worker's Preview Base secrets. Do not copy S3
credentials or `S3_PUBLIC_URL`: preview CMS uploads stay in isolated R2 and
continue using the Worker route. Missing either asset-location value fails
rendering rather than silently using the wrong bucket. All `fileUrl` callers
render on demand (`output: "server"`), so no asset hostname is needed to build.

Audit intrinsic sizes with the repo-level tool: `bun scripts/audit-images.ts
http://localhost:4321/ -v 390 1024 1440` (any page of any website). It loads the
page at each viewport, compares every source with the widest size it renders at,
and flags sources under 3x. `SunPicture`'s default densities (1x-3x) are the
densities the image service serves; the footer logo is a 5x PNG
(`images/logo-horizontal.png`) of the old SVG.

## SEO

`Layout.astro` turns SunLayout's own SEO tags off and renders them with
EmDash's `EmDashHead` (description, canonical, Open Graph, Twitter Card and
JSON-LD). Pages, categories and posts have the **SEO** panel (collection
`supports: ["seo"]`); an empty panel field falls back as follows.

| Page     | Title                             | Description            | Share image                           |
| -------- | --------------------------------- | ---------------------- | ------------------------------------- |
| Home     | `pages` entry `inicio`: its title | Site tagline           | Settings > SEO default, else bucket   |
| Category | `<name> - Pedro Henri Design`     | Category `description` | Category `social_image`, then default |
| Post     | `<title> - Pedro Henri Design`    | Post `description`     | Post `social_image`, `cover`, default |

The home page is the `inicio` entry of the `pages` collection (not routable).
Its **title** field is the home `<title>`; its SEO panel overrides that.
`seed/seed.json` carries the `seo` block of `inicio` and
`settings.seo.defaultOgImage`, but the `emdash seed` CLI and the setup wizard
ignore both (EmDash 1.2.0). `moon run pedrohenridesign:seed` applies them locally
through `scripts/seed-extensions.ts`; CI runs the same insert-only extension
phase after core setup on PR Previews, including retries after HTTP 409.
On a standard Stage database, fill the home SEO panel and **Settings > SEO >
Default Social Image** in the admin. Pages without an image use the resolved
default social image, or `images/imagem-social.png` from the bucket if its
reference cannot resolve; the home title otherwise comes from the entry title.

## Configuration

The canonical host is the Astro `site`. Deploys attach the Stage's Worker
variables, read at request time through `getSecret`: `IMAGES_BASE_URL` from
the deploying job's GitHub environment secret, the rest from Infisical. PR previews use a separate provider flavor; staging and production
share the same standard build artifact.

| Variable          | Purpose                                   |
| ----------------- | ----------------------------------------- |
| `IMAGES_BASE_URL` | `apps/images` transform-service base URL. |

Google Analytics and Google Ads tracking IDs are not variables: edit them in
the admin's **Analytics** page (the `@vandal-websites/emdash-plugin-analytics`
plugin, registered in every environment). Empty IDs disable tracking.

Runtime secrets are every key under Infisical; staging and production each get their own values from Infisical
(`/websites/pedrohenridesign`, environments `staging` and `production`); CI checks them and
injects them at upload (see below). Standard
builds read database and media settings from these values.
PR previews instead use native `DB` (D1) and `MEDIA` (R2) bindings.
`astro dev` ignores deployed providers and uses `.data/`, even when preview
build environment variables are present.

| Secret in Infisical     | Purpose                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `TURSO_DATABASE_URL`    | libSQL database (`libsql://...`)                                                        |
| `TURSO_AUTH_TOKEN`      | Turso auth token                                                                        |
| `S3_ENDPOINT`           | Media bucket endpoint                                                                   |
| `S3_BUCKET`             | Media bucket                                                                            |
| `S3_PUBLIC_URL`         | Optional override for the public media base; otherwise derived from endpoint and bucket |
| `S3_ACCESS_KEY_ID`      | Media bucket credentials                                                                |
| `S3_SECRET_ACCESS_KEY`  | Media bucket credentials                                                                |
| `EMDASH_ENCRYPTION_KEY` | Encrypts plugin secret settings (JMAP credential); one key per Stage                    |

`S3_REGION` (default `auto`) is an optional Infisical key.
`S3_PUBLIC_URL` is optional: deployment and runtime asset helpers derive it from
`S3_ENDPOINT` and `S3_BUCKET` when omitted. An explicitly empty supplied secret is
rejected to prevent inheriting a previous Stage's value.
Astro's `image.remotePatterns` only sees build-time public URLs, not injected
Worker secrets. `SunPicture`
builds external image-service URLs directly and does not need that allowlist.
Shared media resolution, GIF format selection and the Portable Text image
and heading renderers come from `@vandal-websites/sun-ui-emdash`;
`src/components/blocks/PTImage.astro` only adds this site's classes.

`/robots.txt` and `/sitemap-index.xml` are this site's own routes, not the
`robotsSitemap()` integration the other sites use: the sitemap lists the
published categories and posts, read from the CMS on every request, on the
canonical host. Robots allows crawling only on that host.

## Production

Standard staging/production builds read Turso and S3 settings from `process.env`
(`nodejs_compat_populate_process_env` in `wrangler.json`), through
`src/cms/libsql-runtime.ts` and the sun-ui-emdash S3 adapter. The Worker runs
`migrations.runtime: "check"`: it never migrates, so a stopped isolate cannot
leave a migration lock behind, and it answers 503 while migrations are pending.
CI applies the core migrations first: `bun scripts/deploy.ts migrate pedrohenridesign`
runs `emdash migrate` against the stage's Turso database (the `TURSO_*` values
of the stage's Infisical secrets) before the Version is uploaded, on `main`
pushes (staging) and releases (production). A job cancelled mid-migration leaves
a lock; release it by hand with `bunx emdash migrate --status`, then
`--release-lock <id> --expected-target-fingerprint <fp>`, from
`websites/pedrohenridesign`. The seed schema is applied by the setup wizard, which
also creates the first admin and, with **include sample content** checked,
loads the content and downloads the images.

Email goes through the `@vandal-websites/emdash-plugin-jmap` plugin, loaded in builds
only: `astro dev` keeps EmDash's console email provider, so magic links print to
the dev server log. Server URL, authentication (username and password, or a
bearer token), credential, sender address and name, and Reply-To are plugin
settings, entered in the admin under Plugins -> JMAP, not environment
variables. The same page has a "Send test email" action (it uses the saved
settings) and Plugins -> JMAP log lists the last deliveries (status, recipient,
subject, error; never the body). Then pick "jmap-email" under Settings ->
Email. The sender address must match a JMAP identity on the account. The
credential is encrypted with `EMDASH_ENCRYPTION_KEY`, which must be set in the
deployment environment.

Passkeys work only on the hostname that registered them, so register the admin
on `https://pedrohenridesign.com.br`. Until the wizard has run, anyone who reaches an
empty site can finish it and become its admin: run it right after the first
production deploy.

Production uses the Cloudflare Worker `pedrohenridesign` (`wrangler.json`):

| Stage        | Deployed as                                                        | KV namespace               |
| ------------ | ------------------------------------------------------------------ | -------------------------- |
| Pull request | Workers Preview `pr-<N>` of `pedrohenridesign`                     | `pedrohenridesign-pr-<N>`  |
| Staging      | Version of `pedrohenridesign-staging` at 100%                      | `pedrohenridesign-staging` |
| Production   | The same build re-uploaded with production config, at 100% traffic | `pedrohenridesign`         |

Staging and production enable persisted logs, invocation logs, traces, and
real-time issues with 100% sampling. Query strings are not redacted. The
Wrangler `previews.observability` override disables observability for PR previews.

CI runs `scripts/deploy.ts`: selected PR previews build with
`EMDASH_BUILD_FLAVOR=preview`; `main` builds the standard artifact once for
staging, and a release promotes that artifact to production without rebuilding.
Secrets are set per Stage, not with `wrangler secret put`: add the seven required
database, storage and encryption secrets above under `/websites/pedrohenridesign`
in the Infisical `staging` and `production` environments; see the
[provisioning guide](../../docs/guides/provision-new-site-and-rotate-secrets.md).
CI fetches the Stage's file over OIDC, without exposing it to the build, and runs
`scripts/deploy.ts check-secrets`: all seven required keys and every supplied
value must be non-empty. The upload derives `S3_PUBLIC_URL` when absent.
The upload passes them to `wrangler versions upload --secrets-file`, so each
Version carries its own Stage values. A key left out would be inherited from
the previous Version (production would get staging's database), which is why
it is checked. A value set by hand with `wrangler secret put` is overwritten by
the next upload, and a key removed from Infisical stays on the Worker until you
delete it with `wrangler secret delete`. `CF_ACCESS_AUDIENCE` lives on the
`pedrohenridesign-staging` Preview Base, not in Infisical. That Preview Base
also needs staging `S3_ENDPOINT` and `S3_BUCKET` for public code-owned branding
assets only.

Each PR binds `SESSION` to `pedrohenridesign-pr-<N>`, `DB` to D1 database
`pedrohenridesign-pr-<N>-cms`, and `MEDIA` to R2 bucket `pedrohenridesign-pr-<N>-media`.
Redeploying the same PR reuses them and preserves CMS edits. Closing the PR
removes only its Preview and isolated KV/D1/R2 resources, emptying seeded or
uploaded media before deleting the R2 bucket. Other sites' previews remain
KV-only.

The GitHub secret `CF_ACCESS_TEAM_DOMAIN` is a preview-only build input
(hostname or full HTTP(S) team URL, normalized to hostname); missing or invalid
input fails the selected preview build. Set `CF_ACCESS_AUDIENCE` on the
`pedrohenridesign-staging` Preview Base config with
`wrangler preview base-config secret put <key> --worker-name pedrohenridesign-staging`;
it matches the Access application and a missing runtime audience fails
authentication. Add staging `S3_ENDPOINT` and `S3_BUCKET` the same way for
public branding assets, but never Turso/S3 credentials or `S3_PUBLIC_URL`.
Neither audience nor team domain belongs in plaintext stage vars.

Before first access, the operator must protect every preview hostname and all
`/_emdash/*` routes with the intended Access policy. The first trusted
Access-authorized identity becomes the first Admin through native Access.
Bindings create isolated runtime storage, not seeded content or users. Complete
the supported protected setup with `seed/seed.json`, choosing **include
sample content** when desired and continuing native seed progress until it
finishes. The seed has no users. CI provides no public setup bypass or automated
seed/admin-bootstrap step. Access policies and hostname/path coverage are
the operator's responsibility; standard staging/production retain the passkey
setup warning above.

GitHub deploy credentials, required Cloudflare scopes, optional cache secrets
and provider-specific rotation are listed in the
[provisioning guide](../../docs/guides/provision-new-site-and-rotate-secrets.md).
